# Domain Model — NexusMarket

## Introduction

The Domain Model represents the core business entities of NexusMarket, the centralized digital marketplace that intermediates commercial transactions between buyers and sellers. These entities encapsulate the business rules, data, relationships, and lifecycle concepts described in the *NexusMarket Functional Specification*.

The model follows Object-Oriented Design and Domain-Driven Design (DDD) principles. Inheritance is used to represent genuine domain specialization, while explicit object relationships are preferred over generic identifier fields.

The model distinguishes between:

* **Users**, which represent every person authorized to interact with the system and their single, unique role (Dominio 1).
* **Buyers**, which represent users who purchase products (Dominio 2).
* **Sellers**, which represent users who commercialize products and are onboarded exclusively by an Administrator (Dominio 3).
* **Warehouses**, which represent physical storage locations, distinguishing Marketplace warehouses from Seller warehouses (Dominio 4).
* **Products**, which represent the catalog of physical or digital goods offered for sale (Dominio 5).
* **Inventory**, which represents distributed stock linked to a specific Product and Warehouse (Dominio 6).
* **Carts and Orders**, which represent the commercial commitment lifecycle from selection to fulfillment (Gestión del Carrito, Dominio 7).
* **Invoices and Shipments**, which represent the billing and logistics processes generated by an Order (OBJ-09, OBJ-10).
* **Returns and Refunds**, which represent the post-sale process for reversing a commercial transaction (OBJ-11).

A Product may generate multiple Inventory movements throughout its lifecycle, and an Order may generate an Invoice and, when it contains physical products, a Shipment.

# User (Abstract)

## Description

Represents any person authorized to interact with NexusMarket.

This abstract class centralizes the identity, contact, and access information shared by every participant of the marketplace (Buyer, Seller, Logistics Operator, Administrator, Supervisor).

The role assigned to a user determines the responsibilities and business capabilities associated with that user, and each user has exactly one role (RG-02).

This class cannot be instantiated directly.

## Attributes

| Attribute      | Type       | Description                                                                     |
| -------------- | ---------- | -------------------------------------------------------------------------------- |
| identifier     | String     | Unique identifier of the user.                                                   |
| fullName       | String     | Official full name of the user.                                                  |
| email          | String     | Primary means of access and communication. Must be unique across the platform.  |
| role           | SystemRole | Defines the user's responsibilities and permissions. Unique per user (RG-02).    |
| status         | UserStatus | Current operational status of the user (e.g., Active, Blocked).                  |

## Relationships

* A `User` is specialized as exactly one of `Buyer`, `Seller`, `LogisticsOperator`, `Administrator`, or `Supervisor`.
* The `role` belongs to `User` because it represents what the user means within the system and the responsibilities associated with that user.

## Behavior

| Method | Description |
| ------ | ----------- |
| `register(identifier, fullName, email, role)` | Registers the user with its identity data and single role. Rejects a missing role (RG-02). |
| `activate()` | Restores an inactive or blocked user to `ACTIVE`. |
| `block()` | Suspends the user's access. |
| `deactivate()` | Leaves the user registered but unable to operate. |
| `isActive()` | Indicates whether the user's status is `ACTIVE`. |
| `hasRole(expectedRole)` | Indicates whether the user holds the given `SystemRole`. |
| `requireActive()` | Guarantees every operation is executed by an authenticated, active user (RG-01); throws otherwise. |
| `sharesIdentityWith(other)` | Indicates whether two users represent the same identity, used to enforce RG-03 checks in subclasses. |

# Buyer

## Description

Represents a user who participates in commercial processes by purchasing products.

A buyer never administers information belonging to other buyers, nor inventory information, consistent with the key restriction of Dominio 2.

## Inherits From

`User`

## Attributes

| Attribute            | Type            | Description                                            |
| -------------------- | --------------- | ------------------------------------------------------- |
| primaryAddress       | String          | Habitual location used for deliveries.                  |
| additionalAddresses  | List\<String\>  | Optional secondary delivery locations.                   |
| commercialStatus     | CommercialStatus| Condition of the buyer that determines their ability to make purchases. |
| cart                 | Cart            | Buyer's current shopping cart.                            |
| orders               | List\<Order\>   | Orders placed by the buyer. Empty by default.             |
| returns              | List\<Return\>  | Return requests submitted by the buyer. Empty by default. |

## Relationships

* A `Buyer` owns exactly one active `Cart`.
* A `Buyer` places zero or more `Order` instances.
* A `Buyer` requests zero or more `Return` instances.
* `orders` and `returns` are not populated by default; they are loaded on demand.

## Behavior

| Method | Description |
| ------ | ----------- |
| `registerCommercialProfile(primaryAddress)` | Sets the delivery address, enables the buyer commercially, and opens its `Cart`. |
| `addAdditionalAddress(address)` / `removeAdditionalAddress(address)` | Manage secondary delivery locations. |
| `restrictCommercially()` / `suspendCommercially()` / `enableCommercially()` | Change the buyer's `CommercialStatus`. |
| `canPlaceOrders()` | Indicates whether the buyer is active and commercially enabled. |
| `requireEligibleToPurchase()` | Guarantees the buyer can start a purchase; throws `BuyerNotEligibleException` otherwise. |
| `registerOrder(order)` / `registerReturn(returnRequest)` | Link a newly created `Order` or `Return` to this buyer. |
| `owns(order)` | Confirms an order belongs to this buyer, enforcing that a buyer never administers another buyer's information. |

# Seller

## Description

Represents a user responsible for registering and administering their own products.

Sellers cannot self-register; they are always incorporated by an `Administrator`, as established by the business rule of Dominio 3.

## Inherits From

`User`

## Attributes

| Attribute     | Type                     | Description                                            |
| ------------- | ------------------------ | -------------------------------------------------------- |
| registeredBy  | Administrator            | Administrator who onboarded the seller.                  |
| warehouses    | List\<SellerWarehouse\>  | Warehouses owned by the seller. Empty by default.         |
| catalog       | List\<Product\>          | Products published by the seller. Empty by default.       |
| refundsInitiated | List\<Refund\>        | Refunds initiated by the seller. Empty by default.         |

## Relationships

* A `Seller` is registered by exactly one `Administrator`.
* A `Seller` owns zero or more `SellerWarehouse` instances.
* A `Seller` publishes zero or more `Product` instances.
* A `Seller` initiates zero or more `Refund` instances for returns on their own products.

## Behavior

| Method | Description |
| ------ | ----------- |
| `onboardedBy(administrator)` | Records the `Administrator` that onboarded this seller; throws `SelfRegistrationNotAllowedException` when no administrator is given. |
| `addWarehouse(warehouse)` | Adds a `SellerWarehouse`, assigning this seller as its owner. |
| `publish(product)` | Adds a product to the catalog and publishes it. |
| `registerInitiatedRefund(refund)` | Links a `Refund` this seller initiated. |
| `owns(product)` | Confirms a product belongs to this seller. |
| `requireOwnershipOf(product)` | Guarantees a seller only administers its own products (RG-03); throws `UnauthorizedDomainAccessException` otherwise. |

## Inherits From

`User`

## Relationships

* An `Administrator` registers zero or more `Seller` instances.
* An `Administrator` registers zero or more `Warehouse` instances.
* An `Administrator` approves or rejects zero or more `Refund` instances initiated by a `Seller`.

## Behavior

| Method | Description |
| ------ | ----------- |

| `approveRefund(refund)` / `rejectRefund(refund)` | Authorizes or denies a `Refund` initiated by a Seller. Each method requires the `ADMINISTRATOR` role. |

# Product (Abstract)

## Description

Represents a good offered for sale in the NexusMarket catalog.

Products are classified as physical (require inventory and dispatch) or digital (delivered immediately after payment), as defined in Dominio 5.

This class cannot be instantiated directly.

## Attributes

| Attribute    | Type          | Description                                     |
| ------------ | ------------- | -------------------------------------------------- |
| identifier   | String        | Unique identifier of the product.                   |
| name         | String        | Commercial name of the product.                     |
| description  | String        | Detailed description of the product.                |
| seller       | Seller        | Seller who publishes and owns the product.          |
| variants     | List\<ProductVariant\> | Differences such as color, size, or model. Empty by default. |
| status       | ProductStatus | Current publication status of the product.          |

## Relationships

* A `Product` is published by exactly one `Seller`.
* A `Product` may generate zero or more `InventoryMovement` instances.
* A `Product` may appear in zero or more `CartItem` and `OrderItem` instances.

## Behavior

| Method | Description |
| ------ | ----------- |
| `register(identifier, name, description)` | Registers the product's identity data, starting as `SUSPENDED`. |
| `type()` | Abstract; returns `PHYSICAL` or `DIGITAL`. |
| `requiresShipment()` | Abstract; indicates whether the product needs a `Shipment`. |
| `publish()` / `suspend()` / `discontinue()` | Move the product through `ProductStatus`. `discontinue()` is final; a discontinued product can never be published again. |
| `addVariant(variant)` | Adds a `ProductVariant` (color, size, model...). |
| `isPublished()` | Indicates whether the product is currently visible in the catalog. |
| `requirePurchasable()` | Guarantees the product can take part in a purchase; throws `InvalidProductException` otherwise. |

# Inventory

## Description

Represents the distributed stock of a specific `PhysicalProduct` in a specific `Warehouse`.

Inventory must always be linked to exactly one product and one warehouse (Dominio 6). Negative stock is never permitted under any circumstance.

## Attributes

| Attribute     | Type            | Description                                    |
| ------------- | --------------- | ------------------------------------------------- |
| identifier    | String          | Unique identifier of the inventory record.         |
| product       | PhysicalProduct | Product to which this stock belongs.               |
| warehouse     | Warehouse       | Warehouse where the stock is held.                  |
| availableQty  | Integer         | Quantity currently available for sale.              |
| reservedQty   | Integer         | Quantity reserved by active carts or pending orders.|
| damagedQty    | Integer         | Quantity marked as damaged and excluded from reservation. |

## Relationships

* An `Inventory` record belongs to exactly one `PhysicalProduct`.
* An `Inventory` record is located in exactly one `Warehouse`.
* An `Inventory` record may generate multiple `InventoryMovement` instances.

## Business Rule

```text
Inventory.availableQty must never become negative.

Inventory marked as DAMAGED or with availableQty = 0
cannot be reserved.
```

## Behavior

| Method | Description |
| ------ | ----------- |
| `open(identifier, product, initialQuantity)` | Opens a stock record for a product; rejects a negative initial quantity. |
| `registerInflow(quantity)` | Adds newly arrived stock to `availableQty`. |
| `reserve(quantity)` | Holds stock for an active cart or pending order; throws `DamagedInventoryReservationException` when nothing is available and `InsufficientInventoryException` when the amount exceeds what is available. |
| `releaseReservation(quantity)` | Returns previously reserved stock to the available pool. |
| `confirmSaleOutflow(quantity)` | Removes previously reserved stock from the warehouse upon a confirmed sale. |
| `adjust(newQuantity)` | Manually corrects the available quantity; never allows a negative value (`NegativeInventoryException`). |
| `registerReturn(quantity)` | Reincorporates stock coming back from an approved return. |
| `markAsDamaged(quantity)` | Moves available stock into the damaged pool, excluding it from reservation. |
| `canReserve(quantity)` / `totalQuantity()` | Query helpers for available capacity and total stock. |

# InventoryMovement

## Description

Represents a significant stock-affecting action executed over an `Inventory` record.

Movements provide traceability of every change applied to distributed stock, analogous to how significant business actions are recorded across the marketplace.

## Attributes

| Attribute      | Type                    | Description                                  |
| -------------- | ----------------------- | ----------------------------------------------- |
| movementId     | String                  | Unique identifier of the movement.               |
| movementType   | InventoryMovementType   | Category of the stock movement.                  |
| quantity       | Integer                 | Quantity affected by the movement.               |
| executionDate  | LocalDateTime           | Date and time when the movement occurred.        |
| performedBy    | User                    | User who registered the movement.                |
| affectedInventory | Inventory            | Inventory record affected by the movement.       |

## Relationships

* One `Inventory` record may generate zero or more `InventoryMovement` instances.
* Each `InventoryMovement` affects one `Inventory` record.
* Each `InventoryMovement` is performed by one `User`.

## Behavior

| Method | Description |
| ------ | ----------- |
| `record(movementId, movementType, quantity, performedBy, affectedInventory)` | Registers a movement, requiring an active user (RG-01) and a positive quantity. |
| `isOfType(expectedType)` | Confirms the movement's `InventoryMovementType`. |

## Examples of Generated Movements

* `INFLOW`
* `RESERVATION`
* `SALE_OUTFLOW`
* `ADJUSTMENT`
* `RETURN`

# Order

## Description

Represents the formal commercial commitment between a buyer and one or more sellers. Its lifecycle is the central process of NexusMarket (Dominio 7).

## Attributes

| Attribute     | Type            | Description                                     |
| ------------- | --------------- | -------------------------------------------------- |
| identifier    | String          | Unique identifier of the order.                     |
| buyer         | Buyer           | Buyer who placed the order.                          |
| items         | List\<OrderItem\> | Products and quantities included in the order.    |
| orderStatus   | OrderStatus     | Current state of the order's lifecycle.              |
| creationDate  | LocalDateTime   | Date and time when the order was created.            |
| invoice       | Invoice         | Invoice generated for this order.                    |
| shipment      | Shipment?       | Shipment generated when the order contains physical products. |

## Relationships

* An `Order` is placed by exactly one `Buyer`.
* An `Order` contains one or more `OrderItem` instances.
* An `Order` generates exactly one `Invoice`.
* An `Order` generates one `Shipment` only when it contains at least one `PhysicalProduct` item.
* An `Order` may originate one or more `Return` requests once finalized.

## Business Rule

```text
A finalized Order (status = DELIVERED_FINALIZED)
cannot be modified under any circumstance.
```

## Behavior

| Method | Description |
| ------ | ----------- |
| `placeFrom(identifier, buyer, cart)` | Converts a buyer's cart into a formal order in `CART` status; requires an eligible buyer and a checkout-ready cart. |
| `submitForPayment()` | Moves the order to `PENDING_PAYMENT`. |
| `markAsPaid(invoice)` | Confirms payment and attaches the generated `Invoice`, moving to `PAID`. |
| `dispatch(shipment)` | Attaches a `Shipment` and moves to `DISPATCHED`; only allowed for orders that require shipment. |
| `confirmDelivery()` | Closes the order as `DELIVERED_FINALIZED`, confirming the shipment's delivery when one exists. |
| `isFinalized()` | Indicates whether the order has reached `DELIVERED_FINALIZED`. |
| `requireModifiable()` | Guarantees the order can still change; throws `OrderAlreadyFinalizedException` otherwise. |
| `requiresShipment()` | Indicates whether any item needs physical dispatch. |
| `totalAmount()` | Sums every `OrderItem` subtotal. |
| `belongsTo(candidate)` | Confirms the order was placed by the given buyer. |

| `request(identifier, order, buyer, reason)` | Submits a return; only a finalized order owned by the requesting buyer can be returned. |
| `approve()` / `reject()` | Move the return from `REQUESTED` to `APPROVED` or `REJECTED`. |
| `complete()` | Closes the return once the returned product has been processed. |
| `isApproved()` | Indicates whether the return is `APPROVED`, a precondition for initiating a `Refund`. |

# Refund

## Description

Represents the monetary reimbursement associated with an approved `Return` (OBJ-11).

## Attributes

| Attribute     | Type          | Description                                          |
| ------------- | ------------- | ------------------------------------------------------- |
| identifier    | String        | Unique identifier of the refund.                          |
| relatedReturn | Return        | Return that originated the refund.                         |
| initiatedBy   | Seller        | Seller who reviews the return and registers the refund.    |
| approvedBy    | Administrator?| Administrator who approves or rejects the refund request.  |
| amount        | BigDecimal    | Amount reimbursed to the buyer.                            |
| refundStatus  | RefundStatus  | Current state of the refund process.                       |
| processedDate | LocalDateTime?| Date and time when the refund was processed.               |

## Relationships

* A `Refund` originates from exactly one `Return`.
* A `Refund` is initiated by exactly one `Seller`, consistent with the Responsibility Matrix (Section 12 of the specification), where both Seller and Administrator participate in refund management.
* A `Refund` is approved or rejected by exactly one `Administrator`. `approvedBy` remains empty while `refundStatus = PENDING`.

## Behavior

| Method | Description |
| ------ | ----------- |
| `initiate(identifier, relatedReturn, seller, amount)` | The Seller registers the refund for an approved return; starts as `PENDING`. |
| `approve(administrator)` / `reject(administrator)` | The Administrator authorizes or denies the refund; throws `SelfApprovalNotAllowedException` if the approver is the same participant who initiated it. |
| `process()` | Completes the reimbursement once it has been `APPROVED`. |
| `isPending()` | Indicates whether the refund still awaits an Administrator's decision. |

## Business Rule

```text
A Refund must be initiated by the Seller responsible for the
returned Product and can only move from PENDING to APPROVED
or REJECTED through an explicit decision made by an Administrator.

The Seller who initiates a Refund cannot also be its approver,
enforcing separation of duties between execution and authorization.
```

# Domain Lifecycle Relationship

The general lifecycle linking a Product to its stock movements is:

```text
Product
    │
    │ significant stock-affecting action
    ▼
Inventory
    │
    │ movement registration
    ▼
InventoryMovement
```

For example, when a buyer's cart reserves stock:

```text
Inventory
    │
    │ reservedQty increases
    ▼
InventoryMovement
       movementType = RESERVATION
       performedBy = Buyer (via checkout process)
```

Similarly, the commercial lifecycle of an Order is:

```text
Cart
    │
    │ checkout
    ▼
Order (orderStatus = PENDING_PAYMENT)
    │
    │ payment confirmed
    ▼
Order (orderStatus = PAID)
    │
    ├── Invoice generated
    │
    │ preparation and dispatch
    ▼
Order (orderStatus = DISPATCHED)
    │
    ├── Shipment
    │      dispatchedBy = LogisticsOperator
    │
    │ delivery confirmed
    ▼
Order (orderStatus = DELIVERED_FINALIZED)
    │
    │ (optional) buyer requests reversal
    ▼
Return
    │
    │ requestedBy = Buyer
    ▼
Refund
    │
    │ initiatedBy = Seller  (refundStatus = PENDING)
    │
    │ approved or rejected by Administrator
    ▼
refundStatus = APPROVED / REJECTED
    │
    ▼
refundStatus = PROCESSED  (only if APPROVED)
```

# Domain Design Rules

## User and Roles

* `Buyer`, `Seller`, `LogisticsOperator`, `Administrator`, and `Supervisor` inherit from `User`.
* `role` is defined in `User` and is unique per user (RG-02).
* Each participant may only administer information within the scope of their own role (RG-03).
* `Seller.registeredBy` is an explicit domain relationship and must not be represented through a generic identifier field.

## Warehouses

* `Warehouse` is abstract; `MarketplaceWarehouse` and `SellerWarehouse` are its concrete specializations.
* A `SellerWarehouse` always references its owning `Seller` explicitly.

## Products and Inventory

* `Product` is abstract; `PhysicalProduct` requires `Inventory` and generates `Shipment`, while `DigitalProduct` does not.
* `Inventory` must always reference exactly one `Product` and one `Warehouse`; it must never be represented as a standalone, unlinked record.
* `availableQty` must never become negative under any circumstance.
* Every stock-affecting action must generate an `InventoryMovement`.

## Orders

* `Order` is the central lifecycle entity of the domain, mirroring the states defined in the specification: Cart → Pending Payment → Paid → Dispatched → Delivered/Finalized.
* A finalized `Order` cannot be modified.
* `Order.shipment` is only populated when the order contains at least one `PhysicalProduct` item.
* Every `Order` generates exactly one `Invoice`.

## Returns and Refunds

* A `Return` always references the `Order` it originates from.
* A `Refund` always references the `Return` that generated it, the `Seller` who initiated it, and the `Administrator` who approves or rejects it, consistent with the Responsibility Matrix in Section 12 of the specification.
* A `Refund` remains in `refundStatus = PENDING` with `approvedBy` empty until an `Administrator` makes an explicit decision.
* The `Seller` who initiates a `Refund` must never also be its approver.

## Value Objects

* Business entities reference Value Objects (see *Domain Value Objects — NexusMarket*) instead of primitive strings for controlled business concepts such as roles, statuses, and product types.
* This approach improves domain expressiveness, consistency, maintainability, and alignment with Domain-Driven Design principles.

## Behavior and Exceptions

* Entities are not anemic data holders: state changes happen exclusively through the methods documented in each entity's **Behavior** section, never through direct field assignment from outside the domain.
* Every method that could violate a business rule validates its inputs and current state before changing anything, and raises a dedicated exception under `application.domain.exceptions` (all extending `DomainException`) when a rule would be broken — for example `NegativeInventoryException`, `OrderAlreadyFinalizedException`, or `SelfApprovalNotAllowedException`.
* This keeps the business rules of Sections 10–11 of the specification (RG-01 to RG-03 and the critical validations) enforced by the domain itself, rather than depending on callers to remember to check them.
